# Дизайн сервісу чернеток відповідей

Документ описує архітектуру та рішення. Це специфікація, за якою писався код, і орієнтир для агента (див. `CLAUDE.md`).

## 1. Потік даних

```
Helpdesk ──POST /webhooks/helpdesk──▶ API (FastAPI)
                                       │  1 транзакція: INSERT ticket ON CONFLICT DO NOTHING
                                       │                + INSERT job(generate_draft)
                                       ▼
                                   PostgreSQL ◀──────────────┐
                                       │  jobs (SKIP LOCKED)  │
                                       ▼                      │
                                   Worker ── KB search (tsvector)
                                       │── rate limiter (PG, 60/хв)
                                       │── Anthropic API (або stub)
                                       ▼
                                 ticket.status = draft_ready
                                       │
Operator ──UI /ui/tickets──▶ approve / reject / regenerate
                                       │ approve: status=approved + job(send_reply) + Idempotency-Key
                                       ▼
                                   Worker ──POST reply_url (Idempotency-Key)──▶ Helpdesk
                                       │ 2xx → sent; 5xx/timeout → retry з тим самим ключем
```

Процеси (docker compose): `db` (Postgres 16), `migrate` (Alembic + seed бази знань, одноразовий),
`api` (вебхук, UI, JSON API), `worker` (генерація та надсилання), `helpdesk-mock` (фейковий хелпдеск).

## 2. Вимоги → рішення

| Вимога | Рішення |
|---|---|
| Хелпдеск чекає ≤ 2 с | Вебхук лише валідує тіло й робить одну коротку транзакцію (`SET LOCAL statement_timeout = 1500ms`). Генерація асинхронна, у воркері. |
| Дублікати, зокрема одночасні | `UNIQUE(event_id)` + `INSERT ... ON CONFLICT DO NOTHING RETURNING id`. Друга конкурентна транзакція чекає на унікальному індексі й отримує «нічого не вставлено». Відповідь: `202 accepted` для нової події, `200 duplicate` для повтору. Обидві 2xx, тож хелпдеск припиняє повтори. |
| Звернення не можна втрачати | Звернення й задача пишуться в Postgres до відповіді 2xx. Якщо БД недоступна, повертаємо 5xx/таймаут і хелпдеск повторить доставку. Черга живе в Postgres, а не в пам'яті, тож рестарт воркера нічого не губить. |
| Пік 500 звернень / 10 хв | Прийом коштує одну вставку. Генерація обмежена лімітом LLM (60/хв ≥ 50/хв у піку). Черга розгрібається з конкурентністю до 30 викликів (5–30 с кожен). |
| LLM 5–30 с, 60 запитів/хв на весь сервіс | Глобальний sliding-window лімітер у Postgres (`llm_request_log` + `pg_advisory_xact_lock`) працює коректно з кількома репліками воркера. Слот береться перед кожним запитом до провайдера, зокрема в stub-режимі. |
| Режим без API-ключа | Клієнт надсилає реальний запит до Anthropic з фіктивним ключем (отримує 401), ігнорує відповідь і повертає статичний JSON після випадкової затримки 5–30 с. Далі той самий парсер і той самий шлях, що для реальної відповіді. |
| Хелпдеск повертає 5xx або таймаутить | Ретраї з експоненційним backoff + jitter, повага до `Retry-After`. Після вичерпання спроб тікет переходить у `send_failed`, і оператор може натиснути «Повторити». |
| Клієнт не має отримати відповідь двічі | (1) Перехід `draft_ready → approved` робиться умовним UPDATE, тож подвійний клік не створить дві відправки. (2) Одна задача `send_reply` на тікет (`UNIQUE(ticket_id, kind)`), яку бере лише один воркер (`SKIP LOCKED` + lease). (3) Кожен запит несе заголовок `Idempotency-Key`: ключ генерується один раз при підтвердженні й не змінюється між ретраями. Якщо хелпдеск зберіг відповідь, але відповідь до нас загубилася (таймаут), повтор з тим самим ключем не створить дубль. |

### Припущення щодо ідемпотентності хелпдеску

Без ідемпотентності на боці хелпдеску exactly-once доставка неможлива в принципі. Якщо запит
дійшов, а відповідь загубилася, клієнт не може відрізнити це від «не дійшло». Тому ми
вимагаємо від API хелпдеску підтримки `Idempotency-Key` (стандартна практика: Stripe,
Zendesk, Intercom тощо) і реалізуємо її в моку. Якщо реальний хелпдеск її не має,
альтернатива — перед повтором після таймауту перевіряти через його API, чи відповідь уже
опублікована (reconciliation). Точка розширення для цього: `app/helpdesk.py`.

## 3. Модель даних

- `tickets`: одне звернення (одна подія вебхука). Поля чернетки (`draft_text`,
  `draft_sources`), фінальний текст (`reply_text`), `reply_idempotency_key`, статуси й часові мітки.
- `jobs`: черга. `(ticket_id, kind)` унікальні. Поля: `status`, `attempts`, `max_attempts`,
  `available_at`, `lease_token`, `last_error`.
- `kb_articles`: статті бази знань + згенерована колонка `search_vector tsvector` (GIN).
- `llm_request_log`: журнал слотів rate limiter'а.

### Стани тікета

```
            webhook
               │
               ▼
             new ──(LLM ok)──▶ draft_ready ──approve──▶ approved ──2xx──▶ sent
              │ ▲                 │   │                    │  ▲
   (ретраї    │ │ regenerate      │   └─reject─▶ rejected  │  │ retry-send
  вичерпано)  │ └─────────────────┴──────────────┘         │  │
              ▼                                (ретраї     ▼  │
       generation_failed ──regenerate──▶ new   вичерпано) send_failed
```

Усі переходи робляться через `UPDATE tickets SET status = :new WHERE id = :id AND status = :expected`.
Якщо оновлено 0 рядків, дія відхиляється (HTTP 409 в API, повідомлення в UI).

### Черга задач

- **Claim:** `UPDATE jobs SET status='running', attempts=attempts+1, available_at=now()+lease
  WHERE id = (SELECT id ... WHERE status IN ('queued','running') AND available_at <= now()
  ORDER BY available_at FOR UPDATE SKIP LOCKED LIMIT 1)`. Для `running` поле `available_at`
  означає кінець lease, тож задачу «впалого» воркера автоматично підбере інший.
- **Fencing:** кожен claim видає новий випадковий `lease_token`. Завершення (`done` / retry /
  `failed`) робиться з умовою `lease_token = :token_цього_claim` і скидає токен. Воркер, у якого
  протух lease, нічого не перезапише, навіть якщо задачу встигли завершити, перезапустити
  (regenerate скидає `attempts` у 0) і знову взяти з тим самим номером спроби. Тобто номер спроби
  як fence не годиться через проблему ABA, а токен годиться.
- Оновлення тікета й завершення задачі виконуються в одній транзакції.
- Під час LLM-виклику з'єднання з БД не тримається.

## 4. База знань і пошук

- 8 статей про вигаданий продукт **ЗвітХаб** (SaaS для звітів і дашбордів) у `kb/*.md`,
  згенеровані LLM. Під час старту (`migrate`) вони upsert'яться в Postgres.
- Postgres не має українського стемера, тому нормалізація виконується в Python
  (`app/kb/text.py`): токенізація, стоп-слова, відкидання одного типового закінчення й обрізання
  до 5-символьного префікса. Та сама функція застосовується до статей і до запиту.
- Пошук: `to_tsquery('simple', 'term1 | term2 | ...')` по `tsvector` з вагами
  (заголовок A, тіло B), ранжування `ts_rank_cd`, top-3.
- Можливе покращення: гібрид з векторним пошуком (pgvector + ембеддинги).
  Для 8 статей і без обов'язкового API-ключа лексичний пошук дає кращий баланс.

## 5. LLM

- Провайдер: Anthropic, модель `claude-opus-5-5` (змінюється через `LLM_MODEL`).
  `effort=low`, бо задача коротка й не потребує глибоких міркувань. Structured outputs
  (`output_config.format` з JSON Schema) дають гарантовано валідний JSON
  `{"reply": str, "sources": [int]}`. Увімкнено server-side `fallbacks: "default"`:
  якщо модель відмовить, запит виконає рекомендована fallback-модель.
- Модель повертає **номери** статей, а посилання підставляє код з бази знань. Так модель не може
  вигадати URL, а оператор бачить джерела окремо.
- Промпт відокремлює текст клієнта тегами й просить не виконувати інструкцій з нього
  (захист від prompt injection). Фінальний захист: людина-оператор.
- Помилки: 429/5xx/529/мережа → retryable (backoff, `Retry-After`); 4xx, refusal, `max_tokens` → permanent
  (`generation_failed`, оператор може натиснути «Згенерувати знову»).
- SDK-ретраї вимкнені (`max_retries=0`): кожна спроба проходить через наш rate limiter і чергу.

## 6. Мок хелпдеску (`helpdesk_mock`)

- `POST /tickets/{id}/replies`: зберігає відповідь і повертає 201. Імітує збої:
  `MOCK_REPLY_FAIL_RATE` (5xx без збереження) і `MOCK_REPLY_LOST_RESPONSE_RATE` (зберігає, але
  «зависає» довше за таймаут клієнта). Підтримує `Idempotency-Key`: повтор повертає
  збережену відповідь. Рахує `duplicate_messages`: однакові відповіді в одному тікеті,
  тобто те, чого бути не повинно.
- Відправник вебхуків: таймаут 2 с, ретраї з backoff, навмисні дублікати (одночасні й
  запізнілі). Сторінка `http://localhost:8001` має форми «створити звернення» та «пік N звернень».
